# 写课程流程

> 触发: “开始今天的学习”“继续”“开始写课”。

## 一、状态原则

课程状态统一为:

```
计划中 -> 课程已写 -> 学习中 -> 待Review -> Review通过
                                   \-> 返工
```

**课程文件写完不等于学习完成。只有Review通过才能进入下一Day。**

## 二、Step 0: 建立基线

先运行:

```bash
python3 scripts/checks.py status
git status --short
```

确认:

- 当前是否有用户正在填写的课程文件。
- 是否有未提交的无关改动。
- docs镜像是否只是源文件变化导致的stale。
- 不覆盖、不清空用户答案。

## 三、Step 1: 定位真实进度

按优先级判断:

1. 用户实际练习与最新Review结果
2. `vault/会话交接.md`
3. 当前阶段细脉络
4. `resources/主脉络.md`

如果状态冲突，先修状态，不直接写下一课。

## 四、Step 2: 规划闸门

检查:

- 当前Day在细脉络中存在。
- 细脉络与主脉络终点一致。
- 前一Day已Review通过。
- 当天目标仍符合阶段容量。

不满足时先走 `roadmap-writing`。

## 五、Step 3: 学习量卡

写课前先形成:

| 项 | 内容 |
|----|------|
| Day类型 | 新知识/强练习/项目/测试 |
| 唯一主目标 | 今天结束能做什么 |
| 时间 | 2.5-3h或3-4h |
| 新概念 | 常规不超过2-3个 |
| 练习范围 | 子练习、块练习、综合 |
| 验收 | 可运行/可测试/可解释的产出 |
| 超量处理 | 删除、选做、后移或拆天 |

用户上一Day不稳定时，默认减量和返工。

## 六、Step 4: 参考源

至少使用2个来源:

1. 1个官方文档或原始教程
2. 1个主课程/项目参考

优先看 `resources/核心学习资源清单.md`，再查大资源库。

搜索时:

- 只围绕当前Day。
- 不因热门资源临时改变阶段目标。
- 文件顶部标注实际使用的来源。

## 七、Step 5: 依赖矩阵

对每个知识点和必做练习记录:

| 项 | 要求 |
|----|------|
| 目标能力 | 这题练什么 |
| 必用技术 | 完成必须会什么 |
| 已教来源 | 历史Day或本节知识点 |
| 是否越级 | 是/否 |
| 处理 | 保留/前移/降级/选做/删除 |

边界:

- 复习题只用历史内容。
- 知识点练习只用历史内容 + 刚讲内容。
- 块练习只用本块之前内容。
- Day综合只用当天已讲 + 历史内容。
- 选做不作为进度门槛。

## 八、Step 6: 写教程

### 结构

1. 课程目标与学习量依据
2. 复习
3. 知识块1: 解释 -> 最小示例 -> 迁移练习 -> 块综合
4. 知识块2...
5. Day综合
6. 验收说明

### 每个新概念的解释顺序

1. 它解决什么问题。
2. 核心对象或机制是什么。
3. 常用参数/输入是什么。
4. 返回或效果是什么。
5. 在量化场景何时使用。
6. 常见坑和边界是什么。

### 示例规则

- 一段示例只服务一个知识点。
- 示例必须小到能解释。
- 示例后练习必须发生迁移。
- 不把完整综合答案拆成多个“示例”提前泄漏。

### 练习规则

- 题面写what，不写how。
- `# ↓ 你的代码 ↓` 下方留空。
- 总练习必须有新的目标、数据关系、约束或判断。
- 不机械追求10-15题；按难度和时间预算安排。
- 每题有可检查的输出或行为。

## 九、Step 7: 四道质量门

### Gate A: 教学

- 新概念是否解释而非堆代码。
- 示例是否最小。
- 量化用途是否真实。

### Gate B: 练习

- 依赖是否不过界。
- 是否需要迁移而非复制。
- 综合题是否真综合。

### Gate C: 容量

- 预计时间是否可信。
- 新概念和练习是否超量。
- 是否有明确验收。

### Gate D: 状态

- 新课标记为“课程已写”，不是“Review通过”。
- 当前用户答案没有被覆盖。
- 下一步写入交接。

## 十、Step 8: 自动验证

按任务运行:

```bash
python3 scripts/checks.py course
python3 scripts/checks.py plans
python3 scripts/checks.py docs
```

课程含可运行代码时，再运行对应文件或最小测试。

## 十一、Step 9: 更新状态

写课完成时:

- 阶段计划: 标记“课程已写”
- 交接: 写明用户应完成的练习和验收
- 主脉络: 通常不更新逐日状态

Review通过时:

- 阶段计划: 标记“Review通过”
- 交接: 更新下一Day和薄弱点
- 必要时写入 `vault/20_WIKI/`

## 十二、Code Review流程

1. 运行每个命名函数和主流程。
2. 检查正确性、边界、依赖和解释。
3. 只指出当前知识范围内的问题。
4. 不顺手重写成高级版本。
5. 记录薄弱点。
6. 全部验收通过后才推进。

## 十三、提交

- 课程完整、检查通过后再提交相关文件。
- 用户正在填写的练习文件不自动清空或归档。
- 工作树有无关改动时缩小提交范围。
